GitHub Copilotにおけるリードエージェント（メインエージェント）とサブエージェント（Subagents）は、複雑なタスクを効率的かつ正確に処理するための、親と子のような関係を持つオーケストレーション（協調動作）の仕組みです。
2つの役割と関係性について分かりやすく解説します。

🧱 2つのエージェントの基本役割


1. リードエージェント（メインセッション）

ユーザー（開発者）と直接対話する司令塔の役割を持つAIエージェントです。
• ユーザーからの「この機能を追加して」「コードレビューをして」といった大まかな指示を直接受け取ります。
• 指示の内容を分解し、どの専門タスクをどのサブエージェントに任せるか（あるいは自分で処理するか）を判断します。

2. サブエージェント（Subagents）

リードエージェントから指示を受けて、特定の専門タスクのみを裏側で実行する作業員です。
• 完全に独立したコンテキスト（文脈）ウィンドウで動作します。
• 「ファイルの調査」「テストコードの生成」「セキュリティチェック」など、与えられたタスクをピンポイントで処理し、結果だけをリードエージェントに報告します。
• VS Codeなどの画面上では、折りたたみ可能なツール呼び出し（Tool Calls）のブロックとして実行ログが表示されます。

🔄 ダイレクト比較：何が違う？


比較項目	リードエージェント	サブエージェント
ユーザーとの対話	直接チャットでやり取りする	裏側で自動実行される（直接話さない）
コンテキスト（記憶）	会話全体の流れを保持	タスクごとにリセット・分離される
得意なこと	方針決定、進捗管理、ユーザーへの最終回答	特定ファイルの精査、並行処理、個別検証


💡 なぜこの仕組みが必要なのか？（導入のメリット）

長文のチャットを続けていると、AIが最初の指示を忘れてしまったり、関係ないコードに引っ張られてバグを生んだりすることがあります。サブエージェントを切り離して動かすことで、以下のメリットが生まれます。
• コンテキスト汚染の防止: 調査や検証のプロセスで発生した「余計な情報（ノイズ）」がメインの会話に残らないため、リードエージェントが賢い状態を維持できます。
• 並行処理による高速化: 複数のファイル修正や、複数観点（セキュリティ、保守性など）のコードレビューを、複数のサブエージェントで同時に並行して実行できます。
• 精度の向上: 新しいまっさらな思考スペース（Fresh Context）でタスクを解くため、複雑な修正でも実装の巻き戻りや手戻りが減ります。

⚠️ 使用上の注意点

サブエージェントを使うと、裏側で複数のAIが同時に思考してツールを叩くため、単一のチャットで動かすよりも消費するトークン量（AIの処理コスト）が大幅に増加し、実行時間も長くなる傾向があります。簡単な質問のときは、サブエージェントを介さない通常のチャットの方が高速で効率的です。
ユーザー自身で独自の役割を持った「カスタムサブエージェント」を定義し、プロジェクトに配置して分業させることも可能です（.github/agents/ 配下の .agent.md ファイルなどで管理）。

⏳ なぜかえって遅くなったのか？（3つの原因）

• コンテキスト（ドキュメント）の再読み込みコスト
工程ごとにエージェントが分かれていると、各エージェントが起動するたびに「要件定義書」や「設計書」といった大量の前提ドキュメントを最初から読み直す（トークン処理する）必要があり、これに最も時間がかかります。
• リードエージェントの「迷い（オーケストレーション）」
エージェントが多すぎると、メインのリードエージェントが「次はどの工程のエージェントに、どう指示を渡すべきか」を判断する推論（思考フェーズ）が何往復も発生し、処理が停滞します。
• ウォーターフォールの「順序性」と相性が悪い
サブエージェントが真価を発揮するのは「複数のファイルを並行して調査・修正する」という並行処理（マルチスレッド）です。上流から下流へ一本道で進むウォーターフォールを愚直に再現すると、1つずつ順番にしか動かないため、単純に「エージェントの起動・終了」の待ち時間だけが積み重なります。

🛑 なぜ複数人のプログラマー構成で遅くなったのか？

原因は、「司令塔（リードエージェント）がワンマンすぎて、指示出しと確認に時間を取られ、プログラマーたちが手持ち無沙汰になっている」状態だからです。
• 原因1：全員に同じ巨大な「設計書」を読ませている（重い）
プログラマーAにもBにもCにも、プロジェクト全体の分厚い設計書を丸ごと手渡して読ませている状態です。AIが起動するたびに全員が同じ長い文章を最初から読み込むため、全員の動きが遅くなります。
• 原因2：リードエージェントが1人ずつ順番に指示を出している（直列処理）
本来は「みんな一斉に作って！」と並行（マルチスレッド）で動かしたいのに、リードエージェントが「Aさん作って…終わった？じゃあ次Bさん作って…」と1人ずつ順番にしか動かしていない（直列処理になっている）可能性が高いです。
• 原因3：成果物の「すり合わせ（マージ）」で混乱している
プログラマー複数が同時にコードを書くと、後からコードを合体させるのが大変になります。GitHub Copilotも、サブエージェントたちがバラバラに出してきたコードをリードエージェントが1つにまとめ、整合性をチェックする「脳内マージ作業」に膨大な時間を費やします。

🛠️ 1. 設計サブエージェントの指示書（.agent.md）の書き方

機能ごとに設計を行うエージェント（例：design-worker.agent.md）のプロンプトの記述例です。ポイントは、「担当外の仕様は勝手に決めさせない（境界線を引く）」ことと「共通ルールを必ず守らせる」ことです。
markdown
# 名前: 機能別設計エージェント (Design Worker)
description: 特定の機能に特化して、基本設計・詳細設計ドキュメントを生成する専門家です。

# 担当範囲（境界線）
- ユーザーから指示された「特定の1機能」のみの設計書を作成・更新してください。
- 担当外の機能や、システム全体の共通仕様（認証、共通DB、共通共通UIコンポーネントなど）を勝手に新設・変更してはいけません。

# 参照データ (Context)
- 必須参照: `docs/shared/common_spec.md` (全体共通仕様・デザインシステム)
- 必須参照: `docs/shared/design_template.md` (設計書のフォーマット)

# 成果物ルール
- 指定されたテンプレート（design_template.md）の章立てを厳格に守ってください。
- 生成した設計書は `docs/features/[機能名]_design.md` として保存してください。
コードは注意してご使用ください。

💬 2. リードエージェント（PM）への指示の出し方（プロンプト例）

実際にチャット画面からGitHub Copilotに依頼する際は、「共通ルールがあること」「それぞれを別々のサブエージェントで並行処理すること」を明示します。
チャットでの指示文の例：
「docs/shared/common_spec.md（共通仕様）」と「docs/shared/design_template.md（テンプレート）」をベースにして、以下の3つの機能の設計書を同時に作成してください。
1. ユーザー管理機能（出力先: docs/features/user_management_design.md）
2. 決済機能（出力先: docs/features/payment_design.md）
3. 通知機能（出力先: docs/features/notification_design.md）

各機能の設計は、それぞれ独立したサブエージェントを立ち上げて、並行（マルチスレッド）で実行してください。 直列ではなく、同時に処理を開始して工期を短縮してください。

💡 成功させるための3つの極意

1. ドキュメントのフォーマットはMarkdown（.md）が最適
WordやExcelの設計書だと、AIが裏側でファイルを読み書きする際のオーバーヘッドが大きくなり、速度が落ちます。Markdown形式であれば、GitHub Copilotが最も高速かつ正確に読み書きできます。
2. 「共通仕様（共通の型・共通コンポーネント）」を最初に固める
例えば、A機能のエージェントが「ユーザーIDは文字列型（String）」と想定し、B機能のエージェントが「ユーザーIDは数値型（Int）」と想定して設計書を書いてしまうと、後で破綻します。テーブル定義の共通部分や、APIの共通共通ルールだけは、事前に1つのファイル（common_spec.mdなど）に記述して、すべてのサブエージェントに読み込ませてください。
3. 成果物のマージは「ファイル単位」で分ける
1つの大きながんじがらめの設計書ファイルを複数エージェントで同時に編集しようとすると、競合（コンフリクト）が起きてAIの脳内処理がパンクします。必ず [機能名]_design.md のように「1つの機能＝1つのファイル」に切り分けて出力させてください。
この体制を作れば、人間が5人で手分けして設計書を書くのと同じ（あるいはそれ以上の）スピード感で、各機能の設計が同時に立ち上がってきます。

🧠 なぜ「質問専用サブエージェント」を分けると速くなるのか？

理由は、AIにかかる「メモリ（コンテキスト）の体重制限」にあります。
• これまでの問題点（開発と質問の混同）
設計書をガシガシ書いている同じチャット画面で「これってどういう意味？」と質問すると、リードエージェントは「これまでの膨大な設計プロセス」や「他のファイル」をすべて頭に抱えた重い状態（巨大なコンテキスト）で回答するため、一言の返答を出すだけでも数十秒かかってしまいます。
• 質問専用エージェントを分けるメリット
質問エージェントは、成果物を新しく作成したりファイルを書き換えたりする「重いツール（ファイル書き込み権限など）」を持ちません。「渡された資料を読んで答えるだけ」の身軽な状態（読み取り専用）で起動するため、チャットのレスポンスが圧倒的に速く、トークンコストも最小限で済みます。
